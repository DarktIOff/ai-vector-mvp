# ИИ-ВЕКТОР — бриф на разработку frontend

## 1. Назначение документа

Этот документ описывает пользовательский интерфейс системы «ИИ-ВЕКТОР» и может использоваться как самостоятельное задание для Codex на создание frontend-прототипа.

На первом этапе требуется создать качественный интерактивный frontend на тестовых данных. Архитектура интерфейса должна позволять впоследствии подключить реальные сервисы расчётов, формирования отчётов, поиска по базе знаний и локальную языковую модель без существенной переработки компонентов.

Интерфейс и весь пользовательский текст должны быть на русском языке.

## 2. Что представляет собой ИИ-ВЕКТОР

«ИИ-ВЕКТОР» — система подготовки, анализа и проверки статистической налоговой отчётности с применением детерминированных расчётов и технологий искусственного интеллекта.

Система должна помогать пользователю:

- формировать стандартные статистические и аналитические отчёты;
- создавать собственные форматы отчётов на основе шаблонов Word и тегов;
- задавать вопросы к доступным данным на естественном языке;
- находить отклонения и неблагоприятные показатели;
- выполнять углублённый анализ с последовательной детализацией от сводного показателя до его составляющих;
- видеть исходные данные, формулы, источники и ограничения каждого результата;
- проверять, корректировать и утверждать подготовленный системой отчёт;
- сохранять удачные аналитические сценарии и повторно применять их;
- запускать формирование регулярных отчётов по расписанию или после обновления данных.

ИИ применяется для понимания запроса, поиска релевантных методических материалов, подготовки пояснительного текста и помощи пользователю. Расчёт официальных числовых показателей должен выполняться проверяемыми правилами и запросами к данным, а не языковой моделью.

## 3. Этапы развития продукта

### Этап 1 — MVP

Первая версия демонстрирует совместную автоматизированную подготовку отчёта 1-МСП на основе уже имеющихся наработок AutoReport_Windows и AutoMSP.

Frontend MVP должен показывать полный пользовательский сценарий:

1. выбор отчёта 1-МСП;
2. указание территории и отчётных периодов;
3. загрузка или выбор необходимых исходных наборов данных;
4. автоматические проверки входных данных;
5. запуск расчёта;
6. отображение этапов выполнения;
7. получение таблиц, показателей и подготовленного ИИ пояснительного текста;
8. просмотр источников и предупреждений;
9. проверка и утверждение человеком;
10. экспорт результата.

Для frontend-прототипа реальные расчёты не требуются: сценарий должен работать на правдоподобных демонстрационных данных.

### Этап 2 — целевая система

После MVP система должна охватывать утверждённые статистические формы и поддерживать последовательную детализацию:

**Российская Федерация / регион → бюджет → налог → вид экономической деятельности по ОКВЭД → налогоплательщик → декларация, платёж и доступные сведения ККТ.**

Доступность каждого уровня зависит от прав пользователя и фактически подключённых источников.

## 4. Основной образ интерфейса

Интерфейс должен быть минималистичным и визуально близким к настольным приложениям ChatGPT и Claude: спокойный фон, много свободного пространства, центральная рабочая область и две сворачиваемые боковые панели.

Это не обычный чат. Диалог является главной точкой входа, но ответы системы должны включать структурированные аналитические блоки: показатели, таблицы, графики, источники, предупреждения и действия.

### Общая компоновка

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ ИИ-ВЕКТОР   Контекст: 1-МСП · Регион · Период       Тема       Пользователь │
├──────────────────┬─────────────────────────────────────┬─────────────────────┤
│ ЛЕВАЯ ПАНЕЛЬ     │ ЦЕНТРАЛЬНАЯ РАБОЧАЯ ОБЛАСТЬ        │ ПРАВАЯ ПАНЕЛЬ       │
│                  │                                     │                     │
│ + Новый диалог   │ Диалог, отчёт или анализ            │ Параметры           │
│ Поиск            │                                     │ Источники           │
│                  │ Результаты:                         │ Теги                │
│ Диалоги          │ - вывод                             │ Предупреждения      │
│ ───────────────  │ - показатели                        │                     │
│ Шаблоны          │ - таблицы и графики                 │ Контекст выбранного │
│                  │ - источники и действия              │ объекта             │
│                  │                                     │                     │
│ База знаний      │ [Поле запроса................] [→]  │                     │
│ Настройки        │                                     │                     │
└──────────────────┴─────────────────────────────────────┴─────────────────────┘
```

Обе боковые панели должны независимо сворачиваться. Состояние панелей и выбранная тема сохраняются между сеансами.

## 5. Верхняя панель

Верхняя панель должна быть компактной и содержать:

- название и знак «ИИ-ВЕКТОР»;
- текущий контекст: форма отчётности, территория и период;
- индикатор актуальности данных;
- переключатель светлой, тёмной или системной темы;
- уведомления;
- меню пользователя и его роль.

Контекст можно менять непосредственно из верхней панели. Изменение контекста должно быть явно отражено в диалоге и в результатах, чтобы пользователь не перепутал территории или периоды.

## 6. Левая сворачиваемая панель

Левая панель разделена на две основные части.

### 6.1. Диалоги

Необходимые элементы:

- кнопка «Новый диалог»;
- поиск по названиям и содержанию диалогов;
- закреплённые диалоги;
- недавние диалоги, сгруппированные по дате;
- переименование, закрепление, архивирование и удаление;
- статус диалога: черновик, расчёт выполняется, требует проверки, утверждён;
- контекст диалога: форма, территория и период.

Примеры названий:

- «Отчёт 1-МСП за I квартал»;
- «Снижение поступлений по налогу на прибыль»;
- «Сравнение региона со средним по РФ».

### 6.2. Шаблоны документов

Раздел отображает:

- утверждённые шаблоны;
- личные шаблоны пользователя;
- черновики;
- часто используемые шаблоны;
- кнопку «Создать шаблон»;
- кнопку «Загрузить Word-шаблон».

Карточка шаблона содержит название, назначение, владельца, версию, дату изменения и статус согласования.

Пользователь должен иметь возможность начать новый отчёт из шаблона одним действием.

### 6.3. Нижняя навигация

В нижней части панели:

- «База знаний»;
- «Регулярные задания»;
- «Справочник тегов»;
- «Администрирование» — только для соответствующих ролей;
- «Настройки».

## 7. Центральная рабочая область

### 7.1. Стартовый экран

На стартовом экране в центре располагается крупное поле естественно-языкового запроса.

Над полем:

- короткое приветствие;
- выбранный контекст данных;
- пояснение: «Задайте вопрос, сформируйте отчёт или выберите готовый сценарий».

Под полем — несколько компактных карточек быстрых действий:

- «Сформировать отчёт 1-МСП»;
- «Найти неблагоприятные показатели»;
- «Сравнить регион со средним по РФ»;
- «Объяснить изменение поступлений»;
- «Создать отчёт по шаблону».

### 7.2. Поле запроса

Поле запроса закрепляется внизу рабочей области после начала диалога.

Оно должно поддерживать:

- многострочный текст;
- прикрепление файлов;
- выбор режима: «Вопрос», «Анализ», «Отчёт»;
- отправку по `Ctrl/Cmd + Enter`;
- остановку формирования ответа;
- повтор запроса;
- отображение выбранного контекста;
- подсказки команд без необходимости знать специальный синтаксис.

Примеры запросов:

- «Сформируй проект отчёта 1-МСП за I квартал и сравни с прошлым годом»;
- «Почему снизились поступления по налогу на прибыль в регионе?»;
- «Покажи три вида деятельности, сильнее всего повлиявшие на снижение»;
- «Сравни темпы роста поступлений региона со средними по Российской Федерации»;
- «Добавь эту таблицу и вывод в проект отчёта».

### 7.3. Ответ системы

Ответ не должен выглядеть как длинное неструктурированное сообщение. В зависимости от запроса он состоит из следующих блоков:

1. **Краткий вывод** — ответ на вопрос в нескольких предложениях.
2. **Ключевые показатели** — компактные карточки со значением, изменением и статусом.
3. **Таблица** — исходные и рассчитанные значения с единицами измерения.
4. **График** — динамика, сравнение или структура показателя.
5. **Основные факторы** — вклад налогов, отраслей, территорий или плательщиков.
6. **Сигналы «светофора»** — нормальное, требующее внимания или неблагоприятное значение.
7. **Источники и методика** — ссылки на формы, строки, таблицы, даты загрузки и правила расчёта.
8. **Предупреждения** — неполные данные, несопоставимые периоды, отсутствие доступа или другие ограничения.
9. **Действия** — продолжить детализацию, добавить в отчёт, сохранить сценарий или экспортировать.

Любой важный числовой вывод должен иметь действие «Показать расчёт».

### 7.4. Последовательная детализация

Для неблагоприятного показателя пользователь нажимает «Углубить анализ». Система показывает следующий доступный уровень детализации и сохраняет цепочку переходов.

Пример цепочки:

```text
Поступления региона
  → налог на прибыль
    → обрабатывающие производства
      → группа налогоплательщиков
        → конкретный налогоплательщик
          → декларация / платёж / доступные сведения ККТ
```

Над результатом отображается навигационная цепочка, позволяющая вернуться на любой предыдущий уровень. Если уровень недоступен, система должна показать понятную причину, а не пустой экран.

### 7.5. Рабочее пространство отчёта

Отчёт открывается как отдельный режим центральной области и включает:

- оглавление или список разделов;
- редактируемый пояснительный текст;
- вставленные показатели, таблицы и графики;
- отметки о происхождении каждого элемента;
- комментарии проверяющего;
- версии и историю изменений;
- общий статус: черновик, требует проверки, возвращён на доработку, утверждён;
- действия «Предварительный просмотр», «Отправить на проверку», «Утвердить», «Экспортировать».

ИИ-текст всегда должен быть визуально отделён от подтверждённых фактических данных и доступен для редактирования человеком.

## 8. Правая контекстная панель

Правая панель небольшая, сворачиваемая и меняет содержимое в зависимости от выбранного объекта.

Рекомендуемые вкладки:

### 8.1. «Параметры»

- территория;
- отчётный и сравнительный периоды;
- форма отчётности;
- бюджет;
- налог;
- ОКВЭД;
- единицы измерения;
- тип сравнения;
- пороговые значения.

### 8.2. «Источники»

- название источника;
- форма, раздел, строка и графа;
- дата и версия данных;
- применённое правило или формула;
- статус проверки;
- ссылка «Открыть первичные данные» при наличии права.

### 8.3. «Теги»

- поиск по справочнику;
- выбранные теги документа;
- описание выбранного тега;
- тип результата: значение, таблица, график, список, условный или повторяющийся блок;
- правило вычисления;
- доступные параметры;
- статус: корректен, неизвестен, устарел, нет данных, нет доступа;
- кнопка «Проверить тег».

На более позднем этапе можно добавить перетаскивание тегов в редактор шаблона. Для MVP достаточно выбора и вставки.

### 8.4. «Предупреждения»

- неполный набор данных;
- найденные расхождения;
- устаревший источник;
- несовместимые параметры;
- отсутствующие теги;
- ограничения доступа;
- результаты, требующие ручной проверки.

Количество критичных предупреждений должно быть видно даже при свёрнутой панели.

## 9. Экран формирования отчёта 1-МСП

Это главный демонстрационный сценарий MVP.

### Входные параметры

- территория;
- отчётный период;
- период сравнения;
- набор или версия данных 1-МСП;
- данные о поступлениях;
- справочники кодов;
- шаблон итогового документа.

Frontend может имитировать загрузку файлов или позволять выбрать заранее подготовленный демонстрационный набор.

### Этапы обработки

Показывать понятный индикатор выполнения:

1. проверка комплектности;
2. проверка структуры и форматов;
3. сопоставление кодов и показателей;
4. расчёт сравнений и вкладов;
5. формирование таблиц;
6. подготовка пояснительного текста;
7. контроль результата;
8. проект отчёта готов.

Нужно предусмотреть состояния ошибки и повторного запуска отдельного этапа.

### Результат

Демонстрационный отчёт должен содержать:

- основные показатели 1-МСП;
- сравнение двух периодов;
- изменение в абсолютном и относительном выражении;
- структуру поступлений;
- факторы роста или снижения;
- виды экономической деятельности с наибольшим вкладом;
- табличные приложения;
- подготовленный ИИ проект аналитического пояснения;
- источники каждого показателя;
- перечень предупреждений и допущений;
- отметку о проверке человеком.

### Экспорт

В интерфейсе предусмотреть действия:

- Word;
- Excel для табличных приложений;
- PDF для просмотра;
- сохранение версии в системе.

В frontend-прототипе допускается генерировать демонстрационные файлы или показывать уведомление об успешном экспорте.

## 10. Шаблоны Word и справочник тегов

### Шаблон

Пользователь загружает документ Word, содержащий обычный текст и теги-плейсхолдеры. Система распознаёт теги, проверяет их по справочнику и показывает результат.

Пример условного синтаксиса:

```text
За {{reporting_period}} поступления по региону составили
{{total_revenue}}, что на {{revenue_growth_percent}} отличается
от значения сравнительного периода.

{{table_top_okved}}
```

Конкретный синтаксис тегов может быть изменён backend-командой. Frontend не должен жёстко зависеть от фигурных скобок.

### Справочник тегов

Авторизованный методолог или владелец шаблонов может:

- создать черновик тега;
- указать понятное название и технический идентификатор;
- добавить описание результата;
- выбрать тип результата;
- задать необходимые параметры;
- описать правило получения значения;
- добавить пример результата;
- запустить проверку на тестовых данных;
- отправить тег на согласование;
- создать новую версию тега.

Выполнение произвольного SQL в браузере запрещено. Если в будущем будет предусмотрен SQL-редактор, проверка и выполнение должны происходить только на сервере, с разграничением прав, журналированием и ограничением доступных операций.

## 11. База знаний

Отдельный экран предназначен для методических и нормативных документов:

- описания статистических форм;
- правила агрегации строк деклараций;
- формулы показателей;
- справочники;
- инструкции и методические материалы;
- утверждённые примеры отчётов.

Функции экрана:

- поиск;
- фильтры по типу документа, форме и дате;
- просмотр карточки документа;
- версия и период действия;
- статус актуальности;
- связанные показатели и теги;
- использование документа как источника в ответе.

Ответ, подготовленный с использованием базы знаний, должен содержать ссылки на конкретные документы и фрагменты. Если подтверждающего документа нет, система должна явно об этом сообщить.

## 12. Регулярные задания

Экран планирования может быть реализован после основного MVP, но его место следует предусмотреть в навигации.

Пользователь сможет:

- создать регулярное формирование отчёта;
- выбрать шаблон, территорию и периодичность;
- запускать задание по расписанию или после обновления набора данных;
- указать проверяющего;
- просматривать историю запусков;
- повторно запускать завершившееся с ошибкой задание;
- получать уведомление о готовности или проблеме.

## 13. Сигналы и «светофор»

Статусы должны передаваться одновременно цветом, текстом и пиктограммой:

- зелёный — значение в допустимом диапазоне;
- жёлтый — требует внимания;
- красный — неблагоприятное отклонение;
- серый — данных недостаточно или оценка не выполнена.

Для каждого сигнала показывать:

- показатель;
- фактическое значение;
- базу сравнения;
- порог;
- период;
- причину статуса;
- дату расчёта;
- действие «Углубить анализ».

Нельзя полагаться только на цвет: это важно для доступности и однозначности результата.

## 14. Роли и права

Frontend должен поддерживать ролевое отображение функций:

| Роль | Основные возможности |
|---|---|
| Пользователь отчётности | Запросы, запуск утверждённых отчётов, просмотр результатов |
| Аналитик | Углублённый анализ, создание проектов отчётов, сохранение сценариев |
| Проверяющий | Комментарии, возврат на доработку, утверждение |
| Методолог | База знаний, правила показателей, согласование тегов |
| Владелец шаблонов | Создание и версионирование шаблонов и тегов |
| Администратор | Пользователи, права, источники, системные настройки |
| Аудитор | Просмотр журналов, версий, источников и истории действий |

Для прототипа добавить переключатель демонстрационной роли в меню пользователя, чтобы можно было проверить различия интерфейса.

Недоступное действие желательно скрывать. Если оно важно для понимания сценария, его можно оставить заблокированным с пояснением требуемого права.

## 15. Визуальный стиль

### Общие требования

- строгий, современный и спокойный интерфейс;
- минимум декоративных элементов;
- высокая читаемость чисел и таблиц;
- умеренные скругления;
- тонкие границы и мягкие тени;
- единый шаг отступов, предпочтительно 8 px;
- небольшое количество акцентных цветов;
- анимации короткие и функциональные;
- отсутствие визуального образа «волшебного ИИ»: главное — надёжность, проверяемость и контроль.

### Светлая тема

Ориентировочная палитра:

- основной фон: `#F5F7FA`;
- поверхность: `#FFFFFF`;
- основной текст: `#172033`;
- вторичный текст: `#667085`;
- граница: `#E2E7EE`;
- акцент: `#2F6FED`.

### Тёмная тема

Ориентировочная палитра:

- основной фон: `#0D1117`;
- поверхность: `#151B23`;
- приподнятая поверхность: `#1B2430`;
- основной текст: `#E6EDF3`;
- вторичный текст: `#9AA7B5`;
- граница: `#2B3542`;
- акцент: `#6EA8FE`.

### Служебные цвета

- успех: `#2CA66F`;
- внимание: `#D99A16`;
- критическое отклонение: `#D84A4A`;
- информационный: `#3B82F6`.

Все цвета следует оформить через дизайн-токены или CSS-переменные. Необходимо проверить контрастность текста и элементов управления.

## 16. Таблицы и графики

### Таблицы

Таблицы должны поддерживать:

- закреплённый заголовок;
- сортировку;
- фильтрацию;
- изменение ширины столбцов;
- форматирование чисел и единиц;
- выделение отклонений;
- раскрытие строки для следующего уровня детализации;
- копирование;
- экспорт;
- отображение источника выбранной ячейки.

### Графики

Минимальный набор:

- линейная динамика;
- столбчатое сравнение;
- структура показателя;
- вклад факторов в изменение;
- сравнение региона со средним по Российской Федерации.

Графики должны иметь табличное представление данных и корректно работать в обеих темах.

## 17. Состояния интерфейса

Для каждого основного компонента предусмотреть:

- начальное пустое состояние;
- загрузку;
- потоковое формирование ответа;
- успешный результат;
- предупреждение;
- ошибку с понятным дальнейшим действием;
- отсутствие данных;
- отсутствие доступа;
- устаревшие данные;
- прерванный запрос;
- частичный результат;
- необходимость проверки человеком.

Сообщения об ошибках должны быть прикладными. Вместо «Ошибка 500» показывать, например: «Не удалось получить данные о поступлениях за выбранный период. Проверьте доступность источника или повторите запрос».

## 18. Адаптивность

Основной сценарий рассчитан на настольный компьютер.

- от 1440 px — одновременно видны три панели;
- от 1024 до 1439 px — правая панель открывается как выдвижная;
- менее 1024 px — обе боковые панели открываются поверх центральной области;
- минимально поддерживаемая ширина — 768 px;
- таблицы на узком экране допускают горизонтальную прокрутку.

При сворачивании левой панели оставить вертикальную полосу с основными пиктограммами.

## 19. Доступность

Необходимо:

- поддержать управление с клавиатуры;
- показывать заметный фокус;
- добавить текстовые подписи и `aria-label`;
- не кодировать состояние только цветом;
- учитывать режим уменьшенной анимации;
- обеспечить достаточную контрастность;
- корректно озвучивать обновление статуса длительного расчёта;
- сохранять читаемый порядок элементов при открытии боковых панелей.

## 21. Слой API и подключение языковой модели

Frontend должен работать через единый слой сервисов. На этапе прототипа используется `MockApiClient`; позднее он заменяется реальным клиентом.

Ожидаемые группы методов:

```text
GET    /api/chats
POST   /api/chats
POST   /api/query
POST   /api/query/{id}/cancel
GET    /api/reports/{id}
POST   /api/reports/generate
POST   /api/reports/{id}/submit
POST   /api/reports/{id}/approve
GET    /api/templates
POST   /api/templates
GET    /api/tags
POST   /api/tags/validate
GET    /api/sources/{id}
GET    /api/jobs
POST   /api/jobs
```

Для имитации длительных операций предусмотреть потоковое получение событий или абстракцию, которую можно будет подключить к Server-Sent Events либо WebSocket.

### Локальная языковая модель

Наличие локальной языковой модели не является условием для создания frontend. Для демонстрации достаточно подготовленных ответов и имитации потоковой выдачи текста.

Если модель подключается:

- обращение к ней выполняется только через backend;
- frontend вызывает общий метод `/api/query`;
- адрес, провайдер и формат API модели скрыты от компонентов интерфейса;
- API-ключ хранится только в защищённой конфигурации backend;
- запрещено помещать ключ в исходный код, браузерное хранилище или переменные с публичными префиксами наподобие `VITE_` и `NEXT_PUBLIC_`;
- для разных поставщиков должна использоваться единая серверная абстракция провайдера.

## 22. Предпочтительная техническая реализация

Если в целевом репозитории уже выбран стек, следует использовать его. Для нового прототипа предпочтительны:

- React и TypeScript;
- Vite или Next.js;
- CSS-переменные для тем, допустимо применение Tailwind CSS;
- компонентная библиотека без ярко выраженного стороннего визуального стиля либо собственные базовые компоненты;

- лёгкое локальное хранилище состояния для панелей, темы и выбранного контекста;
- ECharts, Recharts или аналогичная библиотека для графиков;
- таблица, способная работать с большими наборами данных и виртуализацией.

Основные компоненты следует строить независимо: `AppShell`, `LeftSidebar`, `TopBar`, `ChatWorkspace`, `PromptComposer`, `ResultRenderer`, `ReportWorkspace`, `RightInspector`, `SourcePanel`, `TagPanel`, `DataTable`, `SignalBadge`, `ReviewControls`.

## 23. Демонстрационные данные

Добавить локальные тестовые данные:

- 8–12 диалогов с различными статусами;
- 6–8 шаблонов, включая утверждённый шаблон 1-МСП;
- 15–20 тегов разных типов и статусов;
- два периода данных для условного региона;
- 5–7 налогов;
- 8–10 видов деятельности по ОКВЭД;
- несколько демонстрационных налогоплательщиков с обезличенными названиями;
- зелёные, жёлтые, красные и серые сигналы;
- источники с формой, строкой, графой и датой версии;
- несколько предупреждений, включая отсутствие данных и отсутствие доступа.

Не использовать реальные персональные, налоговые или конфиденциальные сведения.

## 24. Обязательные интерактивные сценарии прототипа

### Сценарий A — естественно-языковой запрос

1. Пользователь создаёт диалог.
2. Выбирает регион и периоды.
3. Вводит вопрос о снижении поступлений.
4. Видит имитацию потокового ответа.
5. Получает вывод, показатели, график, таблицу, источники и предупреждение.
6. Нажимает «Углубить анализ» и переходит на уровень ОКВЭД.
7. Добавляет результат в проект отчёта.

### Сценарий B — формирование 1-МСП

1. Пользователь выбирает утверждённый шаблон 1-МСП.
2. Заполняет параметры.
3. Выбирает демонстрационный набор данных.
4. Запускает формирование.
5. Наблюдает этапы выполнения.
6. Открывает готовый проект отчёта.
7. Проверяет источник одного показателя.
8. Редактирует ИИ-пояснение.
9. Отправляет документ на проверку.
10. В демонстрационной роли проверяющего утверждает отчёт и запускает экспорт.

### Сценарий C — Word-шаблон и теги

1. Пользователь загружает условный Word-файл.
2. Система показывает найденные теги.
3. Один тег корректен, один устарел, один отсутствует в справочнике.
4. Пользователь заменяет устаревший тег.
5. Создаёт черновик отсутствующего тега.
6. Запускает повторную проверку шаблона.

## 25. Что не следует реализовывать во frontend

- вычисление официальных показателей языковой моделью;
- выполнение SQL в браузере;
- хранение API-ключей и паролей;
- обход ролевых ограничений;
- доступ к реальным декларациям и сведениям ККТ без backend-контроля;
- подмена отсутствующих данных вымышленными значениями;
- утверждение отчёта без явного действия уполномоченного человека;
- жёсткую привязку компонентов к одному поставщику языковой модели.

## 26. Критерии готовности frontend MVP

Frontend-прототип считается готовым, если:

- реализована трёхпанельная компоновка со сворачиванием боковых панелей;
- стартовый экран напоминает по простоте ChatGPT/Claude, но отражает специфику аналитической системы;
- работают светлая, тёмная и системная темы, выбор сохраняется;
- реализованы три демонстрационных сценария из раздела 24;
- диалог поддерживает имитацию потокового ответа и остановку;
- ответы отображаются структурированными блоками;
- доступны таблицы, графики, сигналы, источники и предупреждения;
- работает последовательная детализация хотя бы на трёх уровнях;
- реализовано рабочее пространство проекта отчёта и статусы проверки;
- левая панель содержит диалоги и шаблоны;
- правая панель содержит параметры, источники, теги и предупреждения;
- присутствуют состояния загрузки, ошибки, отсутствия данных и отсутствия доступа;
- интерфейс адаптирован для ширины от 768 px;
- основные функции доступны с клавиатуры;
- в клиентском коде отсутствуют секреты;
- тестовые данные явно обозначены как демонстрационные;
- проект запускается одной документированной командой;
- в `README` описаны запуск, структура проекта и способ замены тестового API реальным.

## 27. Рекомендуемый порядок реализации

1. Создать дизайн-токены, темы и трёхпанельный `AppShell`.
2. Реализовать левую навигацию и центральный стартовый экран.
3. Добавить диалог и универсальный рендерер структурированных результатов.
4. Добавить правую контекстную панель.
5. Реализовать сценарий естественно-языкового запроса.
6. Реализовать мастер и рабочее пространство отчёта 1-МСП.
7. Реализовать шаблоны и справочник тегов.
8. Добавить роли, статусы проверки и экспорт.
9. Проверить адаптивность, доступность и все состояния.
10. Подготовить документацию подключения реального backend.

Главный приоритет — не количество экранов, а цельный и убедительный путь пользователя от вопроса или шаблона до проверяемого проекта отчёта.
