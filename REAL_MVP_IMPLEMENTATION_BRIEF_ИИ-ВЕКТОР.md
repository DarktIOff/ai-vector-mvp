# ИИ-ВЕКТОР — требования к MVP по форме 1-МСП

## 1. Назначение документа

Документ определяет функциональные и технические требования к MVP системы «ИИ-ВЕКТОР» по форме 1-МСП: импорт данных, расчёты, аналитические запросы, формирование отчётов и критерии приёмки.

Документ дополняет frontend-бриф `FRONTEND_BRIEF_ИИ-ВЕКТОР.md`. Frontend должен быть подключён к реальному backend, который:

- загружает исторические файлы 1-МСП в форматах `.xls` и `.xlsx`;
- распознаёт смысл строк и граф формы;
- создаёт единую семантическую модель данных;
- отвечает на вопросы пользователя на естественном языке;
- формирует реальный отчёт Word по логике существующего AutoMSP;
- показывает источники каждого числа;
- использует GLM и Qwen через сменный OpenAI-совместимый слой;
- продолжает выполнять расчёты и формировать отчёт при недоступности языковой модели.

Весь пользовательский интерфейс, сообщения, формируемый отчёт и основная документация должны быть на русском языке.

Также присутствуют служебные файлы macOS и один архив, которые не следует считать наборами данных.

Покрытие:

| Год данных | Наблюдаемая периодичность | Основные форматы |
|---|---|---|
| 2022 | ежемесячные накопительные данные и итог за год | `.xls` |
| 2023 | преимущественно ежемесячные накопительные данные и итог за год | `.xlsx`, отдельные `.xls` |
| 2024 | ежемесячные накопительные данные и итог за год | `.xlsx` |

Это не обычные независимые месячные значения. Значения в форме указываются **нарастающим итогом с начала года** на дату «по состоянию на».

Например:

```text

```

означает период с 1 января по 31 марта 2026 года.

Нельзя суммировать значения за 01.04, 01.07 и 01.10. Для получения отдельного квартала допускается вычислять разность между двумя последовательными накопительными периодами одного года, если схемы сопоставимы.

## 3. Главный архитектурный принцип

### 3.1. Что означает «ИИ понимает строки и графы»

Не следует отправлять целую книгу Excel в языковую модель при каждом вопросе.

Необходима следующая цепочка:

```text
Excel-файлы
  → детерминированное распознавание структуры
  → семантический каталог строк и граф
  → нормализованное хранилище фактов
  → проверяемый план запроса
  → параметризованный запрос к данным
  → пакет фактов с источниками
  → пояснение языковой модели
  → числовая проверка ответа
```

Языковая модель понимает пользовательский язык и выбирает сущности из утверждённого каталога. Она не определяет самостоятельно, в какой случайной ячейке находится официальное число, и не вычисляет его по памяти.

### 3.2. Разделение ответственности

| Задача | Исполнитель |
|---|---|
| Чтение `.xls` и `.xlsx` | детерминированный импортёр |
| Определение версии формы | распознаватель схемы |
| Сопоставление граф и показателей | версионируемый семантический каталог |
| Расчёты, сравнения, доли и разности | backend |
| Поиск данных | параметризованный запрос |
| Понимание естественного запроса | LLM и валидатор плана |
| Формирование исходного фактического текста | детерминированный генератор |
| Стилистическое улучшение текста | LLM, необязательно |
| Проверка чисел и источников | backend |
| Утверждение результата | человек |

### 3.3. Обязательная деградация без ИИ

Если API модели недоступен:

- импорт данных продолжает работать;
- стандартный отчёт 1-МСП формируется;
- таблицы и расчёты доступны;
- естественно-языковой запрос временно недоступен либо работает через ограниченный словарный разбор;
- пояснительный текст формируется детерминированным шаблоном;
- пользователю показывается понятный статус провайдера.

## 4. Что установлено о структуре формы 1-МСП

### 4.1. Разделы

В актуальных книгах:

- **Раздел I** — среднее и малое предпринимательство, включая микропредприятия;
- **Раздел II** — микропредприятия;
- **Раздел III** — малые и средние предприятия без микропредприятий; в источнике может отсутствовать и рассчитывается как `Раздел I − Раздел II`.

Коды строк Раздела II сдвинуты на 1000 относительно соответствующих строк Раздела I:

```text
1010 ↔ 2010
1015 ↔ 2015
1087 ↔ 2087
...
```

Для семантической модели нужен единый `base_row_code`. Для Раздела II:

```text
base_row_code = source_row_code - 1000
```

Раздел III нельзя создавать путём обязательной перезаписи исходных книг. В приложении он должен рассчитываться в памяти или в базе данных с полной ссылкой на два исходных значения.

### 4.2. Строки

В актуальных сводных книгах:

- текст и формула строки находятся в столбце `A`;
- ОКВЭД — в столбце `B`;
- код строки — в столбце `C`;
- числовые значения начинаются со столбца `D`;
- строка `1010` является общим итогом Раздела I;
- строка `2010` является общим итогом Раздела II;
- прочие строки образуют иерархию видов экономической деятельности.

Физический номер строки Excel менялся. Нельзя искать значение по номеру строки листа, например `9` или `10`. Нужно искать по коду из столбца «Код строки».

В старых и региональных книгах физические столбцы также отличаются. Идентификаторами являются:

- раздел;
- код строки;
- номер графы формы;
- территория;
- дата «по состоянию на»;
- версия схемы.

### 4.4. Изменения схемы

Обнаружены как минимум следующие различия:

- в своде за 2023 год — 32 числовые графы;
- в актуальных формах 2024–2025 годов — 43 числовые графы;
- в форме 2026 года — 44 числовые графы;
- в 2022 году и региональных книгах физическое расположение служебных столбцов отличается;
- отдельные периоды содержат единые региональные книги, другие — книги, разбитые по диапазонам кодов строк;
- в некоторых сводах присутствуют служебные листы `hidden*`;
- названия файлов менялись: «Свод по России», «В разрезе субъектов РФ», «Раздел 1», «Раздел I» и другие варианты.

Нельзя определять схему только по году или имени файла.

Для каждой книги необходимо построить `schema_fingerprint`, включающий:

- название формы;
- названия видимых разделов;
- количество граф;
- нормализованные заголовки граф;
- положение строки с номерами граф;
- положение столбца с кодом строки;
- наличие титульного листа;
- хеш нормализованной шапки.

Неизвестная схема помещается в карантин и отображается администратору. LLM может предложить сопоставление неизвестных заголовков, но оно применяется только после проверки человеком.

```text
┌──────────────────┐

         │ REST + SSE

│ Backend API                                         │
│                                                     │
│ Query service   Report service   Catalog service    │
│       │               │                │             │
│       └───────────────┼────────────────┘             │
│                       │                              │
│        Calculation and evidence layer               │
│                       │                              │

└───────────────┬─────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────┐

```

Для локального MVP допустим SQLite. Слой доступа к данным должен позволять перейти на PostgreSQL без изменения бизнес-логики.

Предпочтительный backend:

- Python 3.12;
- FastAPI;
- Pydantic;
- SQLAlchemy;
- Alembic;
- `openpyxl` для `.xlsx` и `.xlsm`;
- отдельный адаптер `.xls`, например `python-calamine` или `xlrd`;
- `python-docx` или `docxtpl` для Word;
- OpenAI Python SDK для обоих OpenAI-совместимых провайдеров;
- pytest.

Если существующий репозиторий уже использует другой сопоставимый стек, следует сохранить его и реализовать те же границы модулей.

## 6. Импорт файлов

### 6.1. Неизменность источников

Все исходные каталоги должны обрабатываться только для чтения.

Запрещено:

- изменять исходные книги;
- добавлять в них Раздел III;
- сохранять пересчитанные формулы поверх оригинала;
- переименовывать или перемещать файлы;
- включать исходные данные в Git.

Каждый импортируемый файл получает:

- абсолютный исходный путь;
- размер;
- дату изменения;
- SHA-256;
- тип;
- дату импорта;
- результат распознавания;
- список предупреждений.

Повторный импорт файла с тем же SHA-256 не должен создавать дубликаты.

### 6.2. Поддержка `.xls`

Поддержка старых `.xls` обязательна.

Рекомендуемый порядок:

1. читать `.xls` специализированной библиотекой;
2. если библиотека не поддерживает конкретную книгу, использовать изолированный адаптер LibreOffice headless;
3. конвертировать только во временный рабочий каталог;
4. не сохранять конвертированный файл рядом с источником;
5. сохранять ссылку на оригинальный `.xls`;
6. очищать временный файл после импорта.

Для LibreOffice должен использоваться отдельный временный профиль, поскольку серверная среда может не иметь доступного пользовательского профиля.

### 6.3. Классификация книг

Импортёр должен различать:

- сводную книгу по Российской Федерации;
- региональную книгу Раздела I;
- региональную книгу Раздела II;
- разбитую региональную книгу по диапазону кодов;
- справочник `Коды.xlsx`;
- книгу общероссийских поступлений;
- управляющую или постороннюю книгу;
- неизвестный формат.

Классификация выполняется по содержимому и структуре, а имя файла используется только как дополнительный признак.

### 6.4. Определение периода

Приоритет:

1. текст «по состоянию на» на титульном листе;
2. текст «по состоянию на» в заголовке раздела;
3. дата каталога — только как проверка, а не основной источник.

Правило:

```text
as_of_date = дата из формы
period_end = as_of_date - 1 день
report_year = год period_end
period_start = 1 января report_year
months_count = месяц period_end
series_kind = cumulative_ytd
```

Если дата внутри книги и дата каталога конфликтуют, импорт не должен молча выбирать одну из них. Нужно записать предупреждение и потребовать проверки.

### 6.5. Распознавание шапки

Необходимо:

1. найти строку с последовательными номерами граф;
2. найти столбцы `А`, `Б`, `В` или их функциональные аналоги;
3. раскрыть объединённые ячейки шапки;
4. для каждой физической колонки собрать путь заголовков сверху вниз;
5. нормализовать переносы, дефисы, неразрывные пробелы и повторяющиеся пробелы;
6. сопоставить полный путь с `metric_definition`;
7. сохранить исходный текст и физическую координату.

Пример:

```text
графа 10
→ в том числе
→ из них
→ налог на добавленную стоимость
→ всего
→ metric_id = receipts_vat_total
```

### 6.6. Распознавание строк

Для сводной книги каждая числовая строка сохраняет:

- исходный код строки;
- базовый код;
- текст строки;
- ОКВЭД;
- уровень иерархии;
- формулу агрегации из текста, если она явно указана;
- раздел;
- координату источника.

Для региональной книги:

- имя листа обычно соответствует коду строки;
- строки данных соответствуют Российской Федерации, федеральным округам и субъектам;
- название территории нужно сопоставлять с единым справочником;
- служебные строки «в том числе» не являются территориями;
- код территории нельзя выдумывать, если его нет в источнике или утверждённом справочнике.

### 6.7. Справочник строк и ОКВЭД

`Коды.xlsx` содержит 66 строк и используется AutoMSP для укрупнённых отраслей. В частности, в нём присутствуют:

- название отрасли;
- диапазон ОКВЭД;
- базовый код строки;
- раздел;
- используемая графа.

## 8. Проверки качества

### 8.1. Структурные проверки

- найдена дата «по состоянию на»;
- найден раздел;
- найден код строки;
- найдена строка номеров граф;
- все обязательные графы сопоставлены;
- единицы измерения определены;
- числовые ячейки действительно содержат числа;
- региональная книга содержит ожидаемые территории;
- отсутствуют дубликаты одной территории на одном листе.

### 8.2. Контрольные соотношения

Если формула явно напечатана в шапке или названии строки, необходимо выполнить проверку с допустимой погрешностью.

Примеры актуальной схемы:

```text
графа 4 = графа 5 + графа 25 + графа 28 + графа 30
графа 5 = графа 6 + графа 8 + графа 10 + графа 12 + графа 19 + графа 24
графа 30 ≥ графа 31 + графа 32 + графа 33 + графа 34 + графа 35
графа 36 = графа 37 + графа 38 + графа 39 + графа 40
```

Для старых схем использовать формулы именно соответствующей редакции формы.

### 8.3. Межфайловые проверки

- значение «Российская Федерация» в региональной книге сопоставляется со сводной книгой;
- сумма Раздела II не должна интерпретироваться как дополнительная к Разделу I;
- Раздел III рассчитывается как разность;
- периоды сравнения имеют одинаковый `months_count`;
- графы двух периодов должны иметь одинаковую семантику, даже если их физические номера отличаются;
- отрицательные значения не заменяются нулём;
- пропуск не заменяется нулём.

### 8.4. Результат импорта

Импорт может иметь состояния:

- `valid`;
- `valid_with_warnings`;
- `quarantined`;
- `failed`.

Пользовательские запросы по умолчанию используют только `valid` и `valid_with_warnings`. Предупреждения передаются в ответ.

## 9. Естественно-языковые запросы

### 9.1. Поддерживаемые вопросы MVP

MVP должен отвечать как минимум на:

- значение показателя за выбранный период;
- сравнение двух сопоставимых периодов;
- темп роста и абсолютное изменение;
- долю микропредприятий;
- значение по малым и средним предприятиям без микро;
- сравнение территорий;
- сравнение территории с Российской Федерацией;
- разрез по укрупнённым отраслям;
- перечень лидеров роста и снижения;
- вклад отрасли в общий объём или изменение;
- вывод источников конкретного числа.

Примеры:

```text
Сколько поступило от МСП за январь-июнь 2026 года?

Сравни поступления НДС от МСП за первое полугодие 2025 и 2026 годов.

Какова доля микропредприятий в поступлениях по УСН?

Какие три отрасли показали наибольший темп роста?

Покажи источник значения по налогу на прибыль.
```

### 9.2. План запроса

Первый вызов LLM должен вернуть только структурированный план:

```json
{
  "intent": "compare",
  "metric_codes": ["receipts_vat_total"],
  "enterprise_groups": ["all_msp"],
  "territories": ["Российская Федерация"],
  "row_codes": [1010],
  "periods": ["2025-06-30", "2026-06-30"],
  "operations": ["value", "difference", "growth_rate"],
  "group_by": [],
  "limit": null
}
```

План проверяется Pydantic-схемой и бизнес-валидатором.

Валидатор обязан:

- разрешить русские синонимы через каталог;
- проверить существование периодов;
- проверить сопоставимость схем;
- проверить права;
- отклонить неизвестный показатель;
- запросить уточнение при существенной неоднозначности;
- ограничить объём результата.

### 9.3. Выполнение

LLM не получает прямого доступа к базе и не выполняет произвольный SQL.

План компилируется backend в параметризованный запрос. Результат формируется как `EvidencePacket`:

```json
{
  "query_plan": {},
  "facts": [
    {
      "fact_id": "fact-...",
      "metric": "НДС",
      "value": "2508.801008",
      "unit": "млрд руб.",
      "period_end": "2026-06-30",
      "section": "I",
      "territory": "Российская Федерация",
      "source": {
        "file": "75638291_1-МСП.xlsx",
        "sheet": "Раздел I",
        "row_code": 1010,
        "report_column": 10,
        "cell": "M9"
      }
    }
  ],
  "calculations": [],
  "warnings": []
}
```

Координата выше приведена как пример структуры ответа. Реальная координата всегда определяется импортёром.

### 9.4. Формирование ответа

Второй вызов LLM получает только:

- исходный вопрос;
- подтверждённый план;
- ограниченный пакет фактов;
- предупреждения;
- инструкции не добавлять новые числа и причины.

Ответ должен содержать ссылки вида:

```text
[Источник 1]
```

Backend сопоставляет их с реальными `SourceReference`.

### 9.5. Числовой контроль

После LLM:

1. извлечь числа из ответа;
2. нормализовать десятичные запятые, проценты, миллиарды и триллионы;
3. проверить каждое существенное число по `EvidencePacket`;
4. разрешить только детерминированно рассчитанные производные;
5. при расхождении отклонить LLM-ответ;
6. показать детерминированный ответ и зарегистрировать предупреждение.

Причинные формулировки запрещены, если причина не содержится в отдельном подтверждённом источнике.

Допустимо:

```text
Основной вклад в увеличение внёс НДС: его поступления выросли на ...
```

если вклад рассчитан.

Недопустимо:

```text
Рост произошёл из-за изменения законодательства...
```

если соответствующий документ или утверждённый комментарий не подключён.

## 10. Реальное формирование отчёта 1-МСП

### 10.1. Эталон

`AutoMSP.bas` является эталоном текущей бизнес-логики. Серверная реализация должна воспроизвести его расчёты, но не обязана воспроизводить технологию VBA, Excel COM и Word COM.

MVP должен работать на macOS, Linux и Windows без установленного Microsoft Office.

### 10.2. Выбор периодов

Для автоматического отчёта:

1. определить последний доступный период;
2. найти тот же `months_count` предыдущего года;
3. проверить сопоставимость показателей;
4. не сравнивать полугодие с кварталом;
5. разрешить пользователю выбрать другую сопоставимую пару.

Для текущего набора AutoMSP рабочая пара:

```text
01.07.2025 → январь–июнь 2025
01.07.2026 → январь–июнь 2026
```

### 10.3. Общероссийские поступления

Из книги поступлений берутся строки:

- `Всего доходов консолидированный бюджет РФ`;
- `Всего доходов по страховым взносам`.

Нужны значения из блока `ПОСТУПИЛО` за старый и новый годы.

Поиск выполняется по нормализованному тексту и многоуровневой шапке, а не по фиксированным координатам.

Единицы:

```text
книга поступлений: млн рублей
итоговый отчёт: млрд рублей
делитель = 1 000
```

### 10.4. Значения 1-МСП

Единицы формы:

```text
1-МСП: тыс. рублей
итоговый отчёт: млрд рублей
делитель = 1 000 000
```

Основные формулы таблицы 1:

```text
RF_total = RF_consolidated_budget + RF_insurance

MSP_budget = section_I(row 1010, receipts_budget_total)
MSP_insurance = section_I(row 1010, receipts_insurance_total)
MSP_total = MSP_budget + MSP_insurance

MSP_share = MSP_total / RF_total × 100

micro_budget = section_II(base row 1010, receipts_budget_total)
micro_insurance = section_II(base row 1010, receipts_insurance_total)
micro_total = micro_budget + micro_insurance

small_medium_budget = MSP_budget - micro_budget
small_medium_insurance = MSP_insurance - micro_insurance
small_medium_total = MSP_total - micro_total

growth_rate = new_value / old_value × 100
difference = new_value - old_value
```

При нулевом знаменателе темп не вычисляется и отображается как отсутствующий показатель, а не как ноль.

### 10.5. Таблица основных налогов

AutoMSP формирует:

- общий объём поступлений МСП в консолидированный бюджет;
- налог на прибыль;
- НДФЛ;
- НДС;
- специальные налоговые режимы;
- УСН;
- АвтоУСН;
- ЕСХН;
- ПСН;
- НПД.

Для каждой налоговой категории:

- МСП, включая микро;
- микро;
- малые и средние без микро;
- старый период;
- новый период;
- темп;
- отклонение.

В актуальной схеме используются графы:

```text
6, 8, 10, 30, 31, 32, 33, 34, 35
```

В коде необходимо обращаться к семантическим идентификаторам, а не к этим номерам напрямую.

### 10.6. Отраслевой блок

Использовать укрупнённые строки Раздела I из `Коды.xlsx`, исключая итоговую строку 1010.

Для каждой отрасли:

- название;
- диапазон ОКВЭД;
- базовый код строки;
- поступления МСП;
- поступления микро;
- поступления малых и средних без микро;
- абсолютное изменение;
- темп;
- доля в общем объёме МСП.

AutoMSP сортирует отрасли по темпу роста для таблицы. Дополнительно интерфейс должен позволять сортировку по объёму, абсолютному вкладу и доле.

### 10.7. Word-шаблон

`template.docx` содержит:

- 20 обычных абзацев;
- 4 таблицы;
- маркеры `tab1_*`, `tab2_*`, `tab3_*`;
- текстовые теги `tag_*`.

Ключевые группы:

```text
{tab1_col_1} ... {tab1_col_4}
{tab1_row1} ... {tab1_row13}

{tab2_col_1} ... {tab2_col_4}
{tab2_row1} ... {tab2_row28}

{tab3_col1} ... {tab3_col6}

{tag_date}
{tag_growth_text}
{tag_growth_percent}
{tag_growth_value}
{tag_budg_growth_txt}
{tag_budg_growth_percent}
{tag_msp_share_txt}
{tag_msp_share_pct_old}
{tag_msp_share_pct_new}
```

Требования:

- работать с копией шаблона;
- сохранить стили, таблицы и русское числовое форматирование;
- динамически изменить число строк отраслевой таблицы;
- не оставить необработанных тегов;
- не повредить объединённые ячейки;
- сохранить документ как `.docx`;
- создать отдельный JSON-снимок фактов отчёта;
- обеспечить повторяемость: одинаковые входные данные дают одинаковые числа.

### 10.8. Пояснительный текст

Сначала формируется детерминированный текст по правилам AutoMSP:

- рост или снижение поступлений МСП;
- итоговый объём;
- рост или снижение совокупных доходов;
- изменение доли МСП;
- две категории налогов с наибольшим абсолютным приростом;
- до трёх отраслей с темпом более 120%;
- три крупнейшие отрасли по доле.

После этого пользователь может включить `Улучшить стиль с помощью ИИ`.

Для LLM передаётся `NarrativeFacts`:

```json
{
  "period_text": "январь–июнь 2026 года",
  "facts": [
    {
      "id": "msp_total_new",
      "value_text": "7,0 трлн рублей"
    }
  ],
  "allowed_claims": [],
  "forbidden_actions": [
    "изменять числа",
    "добавлять причины без источника",
    "скрывать предупреждения"
  ]
}
```

Если проверка улучшенного текста не пройдена, использовать исходный детерминированный текст.

### 10.9. Ручные объяснения из образца

В `Про поступило_V_ИННА_5 месяцев.docx` присутствует блок о законодательных факторах. Эти причины отсутствуют в исходных таблицах 1-МСП и не формируются текущим VBA.

Поэтому:

- считать этот документ образцом оформления, но не полным машинным эталоном;
- не генерировать законодательные причины автоматически из числовой динамики;
- добавить в редактор отчёта отдельный раздел «Подтверждённые факторы»;
- разрешить аналитику ввести фактор вручную и прикрепить источник;
- в будущем заполнять этот раздел через RAG только при наличии методического или нормативного документа;
- помечать неподтверждённый ручной текст соответствующим статусом.

### 10.10. Текущая контрольная выборка

По формулам VBA для пары файлов `53778127_1-МСП.xlsx` и `75638291_1-МСП.xlsx` при чтении текущей книги поступлений получаются следующие контрольные значения до округления:

| Показатель | 2025 | 2026 |
|---|---:|---:|
| Поступления по РФ, млрд руб. | 28 825,079046 | 31 175,605903908297 |
| Поступления от МСП, млрд руб. | 6 088,880300 | 7 000,085844 |
| Доля МСП, % | 21,1235510934 | 22,4537282951 |
| Поступления МСП в консолидированный бюджет, млрд руб. | 4 687,744569 | 5 311,757712 |
| Страховые взносы МСП, млрд руб. | 1 401,135731 | 1 688,328132 |
| Поступления микро, млрд руб. | 2 670,398594 | 2 989,506241 |

Эти значения являются тестовой фиксацией обследованных файлов, а не нормативной константой приложения. Тест должен читать исходники и отдельно сверять расчёт с указанными значениями с малой допустимой погрешностью.

## 11. Подключение моделей

### 11.1. Единый интерфейс

Создать интерфейс:

```python
class LLMProvider:
    async def complete(...)
    async def stream(...)
    async def healthcheck(...)
    def capabilities(...)
```

Реализации:

- `ZAIProvider`;
- `GnivcQwenProvider`;
- `DeterministicProvider` для тестов и аварийного режима.

Оба реальных провайдера используют OpenAI-совместимый клиент.

### 11.2. Конфигурация

Пример `.env.example` без секретов:

```dotenv
LLM_PROVIDER=zai
LLM_QUERY_MODEL=glm-5.1
LLM_NARRATIVE_MODEL=glm-5.1

ZAI_BASE_URL=https://api.z.ai/api/paas/v4/
ZAI_API_KEY=

GNIVC_BASE_URL=https://api.ai.gnivc.ru/v1
GNIVC_API_KEY=
GNIVC_QUERY_MODEL=qwen3.6-35b
GNIVC_NARRATIVE_MODEL=qwen3.6-27b

LLM_TIMEOUT_SECONDS=60
LLM_MAX_RETRIES=2
LLM_DATA_POLICY=metadata_only
ALLOW_EXTERNAL_LLM_DATA=false
```

Имена моделей должны переопределяться без изменения кода.

Не использовать endpoint Z.AI Coding Plan для пользовательских аналитических запросов. Для приложения применяется общий endpoint.

### 11.3. Политика передачи данных

Неизвестно, какие реальные данные разрешено передавать внешнему провайдеру. Нельзя самостоятельно считать такое разрешение предоставленным.

Реализовать режимы:

```text
none          — реальные данные не передаются, только детерминированные функции;
metadata_only — передаются названия показателей и схема, но не значения;
aggregates    — передаются только разрешённые агрегаты;
full          — технически предусмотрен, но выключен по умолчанию.
```

Для Z.AI:

- по умолчанию `ALLOW_EXTERNAL_LLM_DATA=false`;
- healthcheck и тест с искусственными данными разрешены;
- передача реальных агрегатов включается явной настройкой после организационного решения.

Для внутреннего провайдера GNIVC может быть установлена иная политика, но она также задаётся конфигурацией.

### 11.4. Надёжность

Нужно реализовать:

- тайм-аут;
- ограниченное число повторов;
- exponential backoff;
- circuit breaker;
- потоковую выдачу;
- отмену запроса;
- учёт токенов;
- понятные коды ошибок;
- переключение на резервный провайдер;
- детерминированный fallback.

### 11.5. Безопасность секретов

- не читать ключи из `models_and_api_calls.txt` в runtime;
- пользователь добавляет ключ в `.env` или менеджер секретов;
- `.env` входит в `.gitignore`;
- ключ не возвращается через API;
- endpoint статуса показывает только провайдера, модель и доступность;
- ключ не записывается в логи;
- frontend не знает ключ и не обращается к провайдеру напрямую.

## 14. Тестирование

### 14.1. Модульные тесты

- заполнение каждого Word-тега.

### 14.2. Интеграционные тесты импорта

Обязательные образцы:

- `.xls` за 2022 год;
- свод `.xlsx` за 2023 год;
- разделённая региональная книга за 2023 год;
- свод и региональные книги за 2024 год;
- квартальные книги 2025 года;
- книга 2026 года.

Все 166 книг должны:

- успешно импортироваться; либо
- попасть в карантин с конкретной и понятной причиной.

Не допускается молчаливый пропуск файла.

### 14.3. Тест паритета AutoMSP

Для файлов из каталога AutoMSP:

1. определить 01.07.2025 и 01.07.2026;
2. прочитать книгу поступлений;
3. рассчитать таблицы 1–3;
4. сверить контрольные значения раздела 10.10;
5. сформировать `.docx`;
6. проверить наличие четырёх таблиц;
7. проверить отсутствие `{...}`;
8. проверить заголовок «ЯНВ–ИЮНЬ 2025» и «ЯНВ–ИЮНЬ 2026»;
9. проверить все рассчитанные числа до форматирования;
10. проверить открытие итогового документа библиотекой `python-docx`.

### 14.4. Контрольные запросы

Добавить тесты:

```text
Сколько поступило от МСП за январь-июнь 2026 года?

Сравни НДС от МСП за январь-июнь 2025 и 2026 годов.

Покажи поступления микропредприятий по УСН.

Покажи поступления малых и средних предприятий без микро по налогу на прибыль.

Какие отрасли дали наибольший абсолютный прирост?

Откуда взято значение страховых взносов?
```

Проверять не точное совпадение литературного текста, а:

- корректный план;
- корректные факты;
- правильные расчёты;
- наличие источников;
- отсутствие неподтверждённых чисел.

### 14.5. Тест провайдеров

Без ключа:

- приложение запускается;
- `/api/ai/status` возвращает `not_configured`;
- отчёт формируется;
- детерминированный текст создаётся.

С ключом и доступной сетью:

- проходит искусственный healthcheck;
- работает потоковая выдача;
- JSON-план проходит схему;
- при ошибочном ответе включается fallback.

В автоматических тестах не вызывать платный API по умолчанию.

## 15. Нефункциональные требования MVP

- источники открываются только для чтения;
- числа рассчитываются через `Decimal`;
- часовой пояс и локаль задаются явно;
- русское форматирование использует пробел как разделитель тысяч и запятую как десятичный разделитель;
- все длительные операции имеют идентификатор задания;
- импорт и отчёт можно безопасно повторить;
- ошибки не оставляют частично утверждённый отчёт;
- все производные значения имеют происхождение;
- секреты отсутствуют в Git;
- реальные данные не копируются в frontend;
- приложение имеет инструкцию локального запуска;
- Docker Compose приветствуется, но не является обязательным, если мешает доступу к локальным исходным файлам;
- исходные пути задаются конфигурацией.

## 17. Что пока неизвестно и не должно быть выдумано

- окончательная СУБД промышленной версии;
- место промышленного размещения;
- утверждённая схема авторизации;
- организационное разрешение на передачу реальных данных во внешний Z.AI;
- окончательный список ролей и доступов;
- нормативные пороги «светофора»;
- полный набор документов для причинных объяснений;
- правила хранения и удаления журналов;
- необходимость квалифицированной электронной подписи;
- формат промышленной интеграции с источниками вместо файлов.

Для MVP эти пункты оформляются как конфигурация, интерфейс или явно обозначенное ограничение. Нельзя подставлять предполагаемые нормативные значения.

## 19. Критерии готовности

MVP считается работающим, если:

1. приложение запускается без API-ключа;
2. исходные каталоги не изменяются;
3. читаются `.xls` и `.xlsx`;
4. исторические файлы импортируются или получают явный карантин;
5. система различает нарастающий итог и отдельный период;
6. строки и графы представлены семантическими идентификаторами;
7. пользовательский вопрос превращается в видимый проверяемый план;
8. числа берутся из базы, а не генерируются LLM;
9. каждый ответ содержит источники;
10. Раздел III рассчитывается как Раздел I минус Раздел II;
11. реальный отчёт 1-МСП формируется по паре 2025/2026;
12. расчёты отчёта проходят тест паритета AutoMSP;
13. итоговый `.docx` открывается и не содержит тегов;
14. GLM подключается после добавления ключа;
15. Qwen GNIVC подключается тем же интерфейсом;
16. при недоступности модели отчёт продолжает формироваться;
17. LLM не может незаметно изменить число;
18. причины не выдумываются без источника;
19. frontend показывает реальные этапы, данные и ошибки;
20. `README` описывает запуск, импорт, ключи, тесты и ограничения.

## 20. Сквозной сценарий и обработка исключений

Реализация должна обеспечивать полный сквозной сценарий:

```text
реальный Excel
→ импорт
→ проверка
→ семантический факт
→ естественный запрос
→ ответ с источником
→ реальный Word-отчёт
```

Если при реализации обнаруживается новая версия структуры файла:

1. не подгонять данные случайным смещением;
2. добавить тестовый образец;
3. создать или расширить адаптер схемы;
4. сохранить неизвестный элемент в карантин;
5. документировать отличие;
6. продолжить работу с уже поддержанными версиями.

Детерминированный контур должен работать без доступа к API модели. Провайдер проверяется изолированными тестами с mock-ответами; для проверки реального соединения должна быть отдельная команда, выполняемая при доступной сети и настроенном ключе.
